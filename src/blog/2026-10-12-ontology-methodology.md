本体工程比软件工程年轻,工具链弱、失败率高。拍脑袋建的本体大多死于四种死法:**范围失控**(想建"全广告本体")、**术语打架**、**没有评估标准**、**无人维护**。方法论就是防这四死的。

## 方法论谱系

| 方法论 | 年代/出处 | 一句话定位 | 重量 |
|---|---|---|---|
| **TOVE** | 1990s 多伦多 Fox | 企业建模,**CQ(能力问题)概念的祖师爷** | 学派 |
| **斯坦福七步法** | 2001 Noy & McGuinness《Ontology Development 101》 | **施工手册**:单领域小团队入门标准,工业界事实主流 | 轻 |
| **METHONTOLOGY** | 1997 马德里理工 Gómez-Pérez | **项目管理体系**:全生命周期+质量管理 | 重 |
| On-To-Knowledge | 2000s 欧盟 | 骨架法:知识管理视角,5 阶段 | 中 |
| DILIGENT | 2005 欧盟 | **分布式协作**:核心本体+本地扩展,用户/专家分权 | 中 |
| NeOn | 2006 欧盟 | **场景化**:9 种场景(新建/复用/融合/演化/本地化…)各配路线 | 重 |
| 敏捷式(现代实践) | —— | MVP 本体+CQ 回归+迭代演化(与软件敏捷同构) | 轻 |

**共同内核**(所有方法论的生命周期同构):**需求(CQ)→ 概念化 → 形式化 → 实现 → 评估 → 演化维护**。差异只在每阶段做多重、管得多细。

## 斯坦福七步法详解

1. **确定领域与范围**——产出 **CQ 清单**(20~30 个能力问题,本体建成后被什么问题拷问)。易错:范围写成"广告领域"太大,要窄到"供给侧变现口径与路由"这个粒度。冷知识:CQ 概念 1995 年出自 Grüninger & Fox 的 TOVE,七步法是引用者不是发明者;
2. **考察复用可能性**——盘点现有本体/词表(下文展开)。易错:跳过这步闭门造车,结果和 IAB Content Taxonomy 类目对不上,以后对接数据全要翻译;
3. **列出重要术语**——名词表(候选类)+动词/介词(候选关系)。易错:边列边建类——先列全再分类,防止层级被前几个词带偏;
4. **定义类与层级**——三种策略:**自顶向下**(概念驱动)、**自底向上**(从实例/字段反推,数据驱动)、**中间向外**。工业实践**自底向上为主**:从数十个渠道 API 字段和数仓表反推类,防止空中楼阁。易错:is-a 混入 part-of;
5. **定义属性/槽**——数据属性(floorPrice)+对象属性(HAS_SLOT)。易错:把该是属性的做成类——"激励视频"是广告位的样式属性还是子类?**有独立生命周期和关系才是类,否则是属性**;
6. **定义槽的面(facets)**——基数(PDB 保量 deal 恰好 1)、值域、定义域。**这一步就是公理的雏形**——七步法原生就带轻公理;
7. **创建实例**——渠道实例、App 实例入图(MERGE 幂等写入即此步工程化)。

评估兜底(七步法正文外的标配):**CQ 可回答性测试**——拿第 1 步的问题清单逐条问,答不上来就是范围或建模出了问题。

## METHONTOLOGY:三类活动

| 类 | 活动 | 干什么 |
|---|---|---|
| **管理活动** | 计划/调度/控制/质量保证 | 立项、排期、评审门禁——本体当项目管 |
| **开发活动** | 规格化→概念化→形式化→实现→维护 | 概念化阶段产出**独立于实现语言的概念模型**——先画概念图再选 OWL/LPG |
| **支持活动** | 知识获取/整合/评估/文档/**配置管理** | 版本控制、文档、复用整合——一等公民,不是事后补 |

与七步法的本质分工,一句话:**七步法是施工手册,METHONTOLOGY 是项目管理体系**——前者告诉你怎么砌墙,后者告诉你工程怎么立项、验收、管变更。

0→1 场景里 METHONTOLOGY 最值钱的一块是"管理活动+配置管理"的产品化:业务/数仓/分析师要自助维护本体,那**编辑器+审核流+版本发布**就不是锦上添花,是本体能不能活下来的生命维持系统。

## 其他方法论速览

| 方法论 | 记三点 |
|---|---|
| On-To-Knowledge | 5 阶段骨架(可行性→启动→细化→评估→应用演化);知识管理视角 |
| DILIGENT | 分布式团队建本体:**核心本体少数人管+各方本地扩展**,定期修订回核心——多业务线共建时用 |
| NeOn | 9 场景 9 路线:"本体工程是一组可组合的活动"——最接近现代工程观 |
| 敏捷式 | MVP 本体(10 类 20 关系)先上线喂应用 → CQ 回归当测试用例 → 双周迭代 |

**实践中的选型(三合一)**:"**七步法施工、METHONTOLOGY 管骨架、敏捷式定节奏**"——七步法给建法(CQ 驱动、复用行业标准、自底向上建类);METHONTOLOGY 给管理(活动门禁落成编辑器的审核流和版本发布);敏捷式给节奏(MVP 先喂语义层应用,CQ 当回归测试)。

## 已有本体的复用(最容易被低估的一步)

### 为什么复用

不重造轮子;**互操作**(和行业生态对话的通用语);社区验证过(评估成本降);命名与层级可借鉴。复用分四层次:**整体复用 / 部分复用(借类借关系)/ 裁剪复用(简化后用)/ 仅对标参考**(语义映射不引入依赖)。

### 资产清单(广告域视角)

| 资产 | 是什么 | 怎么用 |
|---|---|---|
| **schema.org** | Google/Bing/Yahoo 2011 起的实体词汇表(Organization/CreativeWork/MediaObject/Action…),SEO 生态事实标准 | Organization/Publisher 类对标;创意对齐 CreativeWork——对外交换时语义可互认 |
| **IAB Content Taxonomy 3.0** | 广告内容分类标准(数百类目、3 级层级) | **ContentCategory 类的层级直接挂靠**;对接 DSP 定向/品牌安全 |
| **IAB Audience Taxonomy** | 人群定向分类词表 | 人群标签类对标,圈人语义标准化 |
| **OpenRTB + AdCOM** | 程序化交易协议对象模型(imp/app/site/device/deal/bidfloor)——**竞价侧事实标准** | imp→广告位、app→媒体、deal→PMP 交易——**复用的实战版:不是抄,是映射对齐** |
| **ads.txt / Sellers.json** | 供给链披露标准(谁能卖谁的流量) | 信任域:供给链上游边的行业依据 |
| Dublin Core | 15 元素元数据老标准 | 创意/文档的通用元数据属性 |
| FOAF / SKOS / PROV-O | 人物词汇/知识组织系统/溯源 | **SKOS 直接用**:分类法+同义词的标准形态 |
| Wikidata / DBpedia | 实例级开放知识库 | 媒体/公司实例的富化来源(入图前对齐) |
| FIBO / GO | 金融本体/基因本体(**最成功的本体案例**) | 不直接用——作为"本体要做成什么样"的参照系 |

### 复用的工程动作

①**语义对标(harmonization)**:本地类↔标准类建映射(EquivalentClasses/subClassOf/仅相关),映射关系本身入图;②**命名空间引用**而非拷贝(URI 引用,锁版本号);③**别名保留**(行业叫法进 alias);④**粒度适配**:标准层级太粗/太细时取中间层,裁剪记录在案。

### 复用的坑(说出两个就是老手)

1. **标准会 breaking 升级**:IAB Content Taxonomy 2.x→3.0 类目重构——锁版本,升级走本体演化闭环,不能裸跟;
2. **同名不同义**:标准里的 "Advertisement"/"Video" 与自家类的语义偏差——映射前做语义审查,**宁标 subClassOf 不轻标 equivalent**;
3. **粒度/文化不匹配**:海外标准的分类逻辑与国内渠道生态不完全对齐——复用层级骨架,叶子层本地化;
4. **许可与会员**:IAB Tech Lab 部分规范需会员权限;开源本体看许可(多为 CC-BY,署名即可)。

### 复用决策判据

社区成熟度/与本域贴合度/演化风险(对方 breaking 你跟不跟)/许可成本。**默认答案是混合**:"骨架复用行业标准(IAB/OpenRTB),叶子层本地自建(渠道口径),映射层显式管理"——和建模语言选型里"内核自建、外交标准"完全同构。
